# Supply-chain release gate

The flagship release verifier has a standalone fail-closed supply-chain check:

```bash
python3 /docker/chummercomplete/scripts/release/verify_supply_chain_evidence.py
```

It writes `/docker/chummercomplete/.codex-studio/published/SUPPLY_CHAIN_RELEASE_GATE.generated.json` and deterministic CycloneDX 1.5 inventories under `.codex-studio/published/sbom/`.

The check covers the shipped run-services API and identity projects plus the Avalonia, Blazor Desktop, and desktop-installer dependency surfaces. It performs:

- a redacting signature and sensitive-config scan of Git-tracked files in `chummer.run-services` and `chummer-presentation`;
- `dotnet list package --vulnerable --include-transitive --no-restore` for every target, so the release gate never hides an unavailable restore/audit behind an implicit restore;
- deterministic CycloneDX inventories derived from each target's `project.assets.json`;
- exact digest discovery for the current run-services OCI images and desktop download-manifest artifacts;
- structural verification of a build-time provenance receipt that binds artifact, source commit/tree, and SBOM digests.

`not_available` is release-blocking. In particular, the verifier does not install secret/SBOM/container tools, download mutable vulnerability databases, or synthesize provenance after a build. With no offline container scanner database or build-time provenance receipt, the honest result is `SUPPLY_CHAIN_BLOCKED` even when the built-in secret scan, NuGet audit, and SBOM generation pass.

## Offline container-scan producer

`/docker/chummercomplete/scripts/release/materialize_container_vulnerability_scan_evidence.py` is the governed producer for `chummer6.container_vulnerability_scan_evidence.v1`. It requires explicit absolute paths to an already-installed Trivy or Grype executable, the Docker executable, an existing local scanner cache, its native database file, and its native metadata file. It does not search for, install, download, or update any of them.

For an existing Trivy cache, the operator integration command is:

```bash
python3 /docker/chummercomplete/scripts/release/materialize_container_vulnerability_scan_evidence.py \
  --scanner trivy \
  --scanner-binary /opt/security-tools/trivy \
  --docker-binary /usr/bin/docker \
  --cache-dir /var/lib/chummer-security/trivy \
  --database-artifact /var/lib/chummer-security/trivy/db/trivy.db \
  --database-metadata /var/lib/chummer-security/trivy/db/metadata.json \
&& python3 /docker/chummercomplete/scripts/release/verify_supply_chain_evidence.py
```

For an existing Grype cache, replace `--scanner trivy` and the three Trivy paths with the existing Grype executable, cache, native vulnerability database, and native metadata paths. The producer sets `GRYPE_DB_AUTO_UPDATE=false` and `GRYPE_CHECK_FOR_APP_UPDATE=false` and forces `--from docker`; the Trivy lane uses `--offline-scan`, disables vulnerability, Java, and checks-bundle updates, and forces `--image-src docker`. Scanner configuration runs with an isolated empty home so user-level ignore/filter configuration cannot silently weaken the scan.

The producer always scans the API and identity image names defined by the release target inventory. It records the exact local Docker image IDs before and after each scan and requires each scanner-native JSON document to bind the same image name and ID. It also binds hashes for the scanner and Docker binaries, database, native metadata, and every native result. Database and scan timestamps must satisfy the verifier's freshness policy. Missing or stale inputs, a non-zero scanner exit, unsupported or injected arguments, image/tool/database drift, ignored findings, native identity mismatch, and release-blocking findings all return non-zero. A run first atomically invalidates any older receipt, then atomically publishes the new evidence pointer only after validation; it never leaves an older green receipt authoritative after a failed attempt.

Do not run this command merely to make the gate green. If the named binaries, cache, and current local images are not genuinely available, leave `CONTAINER_VULNERABILITY_SCAN_EVIDENCE.json` unavailable and keep the release blocked.

## Build provenance input

The default input is `.codex-studio/published/BUILD_PROVENANCE.generated.json` with contract `chummer6.build_provenance.v1`. It must be generated by the artifact build and contain one subject per discovered shipped artifact. Each subject binds:

- `artifact_id` and `artifact_sha256`;
- `target_id`;
- `source_repository`, `source_commit`, and `source_tree`;
- the matching generated `sbom_sha256`.

The receipt also requires `builder_id`, `build_type`, `invocation_id`, and `generated_at_utc`. A hand-authored pass receipt after the build is not acceptable evidence.

The build helper is `/docker/chummercomplete/scripts/release/materialize_build_provenance.py`. Its two phases are deliberately split across the actual artifact-producing command:

1. `begin` exclusively reserves a new invocation-specific state and receipt path, rejects tracked source changes, captures the exact commit and tree, declares the expected subject before packaging, and writes the deterministic target SBOM. Concurrent reuse of either path fails closed instead of overwriting another invocation.
2. `finalize` runs only after packaging succeeds and claims a one-time finalization marker. It rejects an unchanged or pre-existing artifact, rechecks the source identity and clean tracked worktree, rechecks the SBOM digest, and binds the exact artifact SHA-256 to the invocation-state digest. Simultaneous or repeated finalization cannot rewrite the receipt; a rebuild must use a new invocation id.

The authoritative `chummer-presentation/scripts/materialize-linux-desktop-exit-gate.sh` lane begins provenance after its isolated-source restore but before the self-contained `dotnet publish`, then finalizes only after `build-desktop-installer.sh` emits the `.deb`. The state binds the original Git source root and the pre-build source-snapshot manifest while the compile and package steps run from that isolated snapshot. A stale publish directory cannot be repackaged into a pass receipt, source-snapshot drift fails finalization, and a dirty tracked source repo stops the build before publish.

### Immutable invocation collection

Producer receipts live under `.codex-studio/published/build-provenance/invocations/<invocation-id>.json`. Linux, Windows, payload, and OCI producers use distinct invocation ids and never write `BUILD_PROVENANCE.generated.json` directly.

`/docker/chummercomplete/scripts/release/collect_build_provenance.py` holds an exclusive collector lock, reads only regular non-symlink JSON receipts whose filename matches their safe invocation id, and writes the canonical aggregate atomically. For every current shipped subject it:

- rejects stale, malformed, dirty-source, artifact-mismatched, or SBOM-mismatched invocation receipts;
- deterministically selects the newest exact matching invocation, using invocation id as the stable tie-breaker;
- embeds the selected immutable receipt and binds its exact file SHA-256;
- emits the exact expected subject set and fails when any current subject is missing;
- never changes an invocation receipt and never manufactures a missing subject.

The Linux producer invokes the collector with `--allow-incomplete`. That flag returns success only when the aggregate's sole failures are explicitly missing producer subjects; source drift, malformed evidence, unsafe files, discovery errors, and other integrity failures still fail the Linux lane. The canonical aggregate remains `status: fail` until every producer exists.

The verifier additionally requires:

- provenance generated within 168 hours (configurable with `--provenance-max-age-hours`), with a valid build-start timestamp;
- a canonical hash of the embedded pre-build invocation state;
- exact subject completeness, including artifact kind/name, invocation id, clean-source assertion, and `produced_during_invocation=true`;
- a separate subject for a Windows bootstrap payload whenever the public download manifest advertises one.

Current limitation: the Linux desktop installer is the first integrated producer. Windows installer, Windows payload, and run-services OCI image builds still need equivalent begin/finalize hooks. Until every current shipped manifest artifact and inspected image ID has a matching fresh immutable receipt, the canonical aggregate and supply-chain gate remain blocked.

## Root release-ready integration

The intended root gate entry is:

```bash
"verify_supply_chain_evidence:python3 $root/scripts/release/verify_supply_chain_evidence.py"
```

Place it immediately after `verify_package_boundaries` so secret, dependency, SBOM, container, and provenance failures stop the same release-ready verdict as the other mandatory gates.
